在 Text Generator 里用 DaoXE

Text Generator 是 Obsidian 里做模板化 AI 的插件。它的自定义供应商接受任何 OpenAI 兼容端点 —— 包括网关 —— 用一个 key 在笔记上跑跨 GPT、Claude、Gemini 的提示词。

更新于 2026-07-20

Text Generator 的 LLM Provider → Custom 只要 endpoint、key 和模型 —— 而它的模板系统意味着改一次，库里的所有命令、按钮和 recipe 都跟着换。最容易踩的坑：和多数客户端相反，它要的是完整端点路径，不是到 /v1 为止的 base URL（最便宜 API 教程）。

为什么让 Text Generator 走 DaoXE#

  • 模板驱动。 Frontmatter 配置、recipe、自定义命令全部继承供应商 —— 配一次就够。
  • 一个 key，多家厂商。 不同任务指向不同模型，不用另开账号。
  • 在笔记库里跑。 总结、抽取、改写都留在 vault 内。

在 Text Generator 里配置#

  1. 打开供应商设置。 Obsidian → Settings → Text Generator → LLM Provider → 选 Custom。
  2. 填完整端点。 填 https://daoxe.com/v1/chat/completions —— 这个插件要完整路径，不是到 /v1 的 base URL。只填 base 会 404。
  3. 加 key 和模型。 粘贴 DaoXE key；模型设为从 GET /v1/models 复制的精确 ID。
  4. 用模板测试。 对一篇小笔记跑任一内置命令；核对响应里的 model 字段与配置一致。

值得注意的坑

完整路径 vs base URL：自定义供应商的 endpoint 字段原样使用 —— 是 …/v1/chat/completions，不是 …/v1。这与多数客户端约定相反，是最常见的配置错误。模板可能硬编码模型：frontmatter 和 recipe 文件可以自带模型字段并覆盖默认值 —— 如果结果来自错误的模型，先查这里。只用精确 ID：模型 ID 与账号绑定；从 GET /v1/models 读取。更多客户端见客户端设置说明。

验证你拿到的是真模型#

先证明端点可用，再怀疑客户端 —— 这一步失败，改任何设置都没用：

bash
export DAOXE_API_KEY="your_api_key"

# List the exact model IDs your account can call
curl --fail-with-body --show-error --silent \
  https://daoxe.com/v1/models \
  -H "Authorization: Bearer ${DAOXE_API_KEY}"

先在客户端之外验证端点，再在 temperature 0 下把难题与官方 API 对比：

bash
curl --fail-with-body --show-error --silent \
  https://daoxe.com/v1/chat/completions \
  -H "Authorization: Bearer ${DAOXE_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "YOUR_EXACT_MODEL_ID",
    "max_tokens": 64,
    "messages": [{"role": "user", "content": "Say hello in one sentence."}]
  }'

常见问题#

Text Generator 能接 DaoXE 吗？

能 —— LLM Provider → Custom，endpoint 填 https://daoxe.com/v1/chat/completions（完整路径），加 key 和精确模型 ID。

为什么 base URL 会 404？

插件不做任何路径拼接 —— 它按原样向 endpoint 发请求。补上 /chat/completions。

不同模板能用不同模型吗？

能 —— 模板 frontmatter 可覆盖默认模型，这正是插件的设计意图。

怎么收费？

按模型、随账号 —— 实时定价；充值统一 1 元 = $1 额度。
